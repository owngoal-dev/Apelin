Apelin 0.4.10 adds custom instructions for all chats and each project, publishes release packages directly to a GitHub Release, imports skills from GitHub, and includes `otool` and `ar` in newly set up toolchains.

- Every project Apelin made required iOS 16.0 and set `firmware (>= 16.0)` in its package, so a tweak or command-line tool could not be installed on an iOS 15 device without editing the package's `control` file by hand, even when the code could run there. A C or Objective-C project can now set the deployment target as low as `15.0` in `apelin-project.json` (or you can ask the agent to change it), which sets `firmware (>= 15.0)` in its package. New projects still start at 16.0, Apelin itself still requires iOS 16.0, and Swift projects still require 16.0; the project check explains that the Command Line Tools lack the Xcode libraries Swift needs on iOS 15.
- To give the agent standing preferences (such as how to reply or what to check first), you had to repeat them in every chat or put an `AGENTS.md` file in each project. You can now write instructions for every chat (up to 2,000 characters) in Settings ▸ Agent ▸ Custom Instructions, and set a project's own instructions from a chat's More menu ▸ Custom Instructions…, which also shows everything that chat loads (All Chats, This Project, and the project's `AGENTS.md` or `CLAUDE.md` read-only). An open chat picks up changes with your next message; project instructions override instructions for all chats where they disagree, and both come before `AGENTS.md` or `CLAUDE.md`, without changing approvals or Apelin's rules.
- On every toolchain Apelin set up, `otool` failed with `can't find or exec … otool-classic` and `ar` with the `s` flag (`ar rcs`) failed with `internal ranlib command failed`, so neither you nor the agent could inspect a binary with `otool` or build a static library with `ar`. Toolchains set up in this version include both. A toolchain set up earlier keeps building as before and notes under its name in Settings ▸ Toolchains: "From an earlier setup. Set it up again to add otool and ar." (or for Command Line Tools 27.0, which Apple no longer offers, "Set up 27.2 to add otool and ar."). To get them, set that release up again from Settings ▸ Toolchains ▸ + so it appears beside the old one, switch your projects to it, and remove the old toolchain when nothing uses it; until then, `libtool -static -o` makes an archive on the old toolchain.
- When the agent confirmed that a tweak loaded, it listened for only 15 seconds (or 30 with a respring), so a tweak targeting a process that starts on demand (such as a daemon launched when a Mac connects or an app you open) could not be confirmed, tapping Stop did not cancel the check, and a tweak that failed to load could not be told apart from a process that never started. The agent now tells you what to start before listening for up to 3 minutes, finishes as soon as it hears the tweak's marker, stops immediately when you tap Stop, and reports whether the target process ran during the check or was already running and needs a restart.
- Publishing packages for a source that reads GitHub Releases (such as `apt.owngoal.dev`) meant creating the release on GitHub by hand, or rebuilding on GitHub Actions, which produced a different package from the one you built and tested on your device, and one whose crashes Apelin cannot symbolicate. Choose Publish to GitHub Release on the distribution page (Distribute… ▸ Packages) or in the build page's Distribute menu (or ask the agent) to publish your on-device release builds as they were built, RootHide and rootless together, to release `v<version>` of the project's GitHub repository, tagged at the pushed commit with a `SHA256SUMS` file. It requires Sign In with GitHub in Settings ▸ Git, asks you to confirm the repository, tag, commit, and packages first, never moves a tag already on another commit, and does nothing if the same packages are published again.
- Skills could only be imported from Files one folder or Markdown file at a time, so you had to download a skill shared on GitHub before importing it. In Settings ▸ Agent ▸ Skills ▸ + ▸ From GitHub…, paste a link to a public repository, a folder in one, or a single `SKILL.md` file to see the skills Apelin finds, preview them, tick the ones you want, and import them with their reference files. Nothing in the repository is run; skills that chats cannot use are shown with the reason and cannot be ticked, and you are asked before replacing a skill with a name you already have.
- If a skill's `SKILL.md` began with an empty header (a `---` line followed immediately by another `---` line) in the skills folder, every chat failed to start and Settings ▸ Agent ▸ Skills failed to load. Importing such a file is now refused, and one already in the skills folder is listed as a problem in Settings ▸ Agent ▸ Skills while your other skills and chats keep working.
- When the agent created a new project and opened a conversation for it, that conversation could open in the chat's current project instead; and when feedback or an issue the agent wrote was refused for private data, the error only said "what looks like a device identifier", leaving the agent unable to tell what to remove. The agent now targets the new project by name and reports which project the conversation opened in, and private-data refusals quote what matched and where (for example, a full 40-character commit reference matches a device identifier, so give commits by their first 7 to 12 characters).
- When the agent wrote a GitHub Actions workflow or inspected a failed run, workflows often failed on the first push over script permissions, unquoted colons in YAML, or unsigned slices on macOS runners, and the agent could not read the failure log without admin rights. The agent now writes workflows with executable scripts, quoted YAML values, and signing for every slice on a macOS runner, and reads a failed run's steps and error messages directly from the conversation.

Requires iOS or iPadOS 16.0 or later, an A12 chip or later, Irisin 4.7.3 or later and icli 0.11.0 or later. Choose the `iphoneos-arm64e` packages for RootHide or the `iphoneos-arm64` packages for rootless, and check each download against `SHA256SUMS`.
